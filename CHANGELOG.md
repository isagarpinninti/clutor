# Changelog

Format follows [Keep a Changelog](https://keepachangelog.com/); versions follow [Semantic Versioning](https://semver.org/).

## Unreleased

- **Engine speed.** Prompt processing is now batched for every architecture (it was only batched for qwen35): each weight matrix is read once per batch of up to 64 prompt tokens, and in a mixture-of-experts layer each chosen expert is read once per batch for all the tokens that picked it (so a long prompt streamed from disk reads each expert once per layer-batch instead of once per token; verified for correctness on the test models, not yet measured on a large MoE). The 128,000-word output layer is computed for the last prompt token only. Attention runs across all threads (one task per head and token), which matters most at long contexts, and the half-precision conversion in the matrix kernels uses the processor's own instruction. The batched path gives **bit-identical logits** to stepping token by token on all six architectures, mapped and streamed, at several batch sizes (new `make prefill-test`, in CI, also under ASan and TSan). On the development Mac (M2, Llama 3.2 1B Q4_K_M, same-session measurements): prefill 38 to 84 tokens/s at ~500 tokens of context, 18 to 59 at ~2,000 and 9.5 to 26 at ~6,000; generation 26 to 29, 14 to 24 and 6.4 to 13 tokens/s. A first run measured up to 4x for prefill; this machine's speed varies with load, so the conservative same-session figures are the ones to trust. Generation speed on short contexts is limited by memory bandwidth and did not change much.
- Fixed a data race (found by ThreadSanitizer) in the lazily initialised float-math flag that every pool thread reads.

- **Will it run?** In the app, each model has a "Will it run?" check: it reads only the model's header and says whether the model fits, where the memory goes, and the fastest the disk could let it generate (computed upper bounds), with **Measure this disk** to replace the assumed 3 GB/s by a timing of the model's own file. The terminal app has the same: `clutor plan <file.gguf> --measure-disk` (via the new engine command `clutor-engine diskbench`). On the development Mac the measured scattered read speed was 1.27 GB/s, not the assumed 3.
- **Windows and Linux:** the desktop app is now built and tested by CI on macOS, Windows and Linux (it had only ever been compiled on macOS). The engine gained a small threading layer so it builds with the normal Windows compiler (clang-cl); commands the agent runs on Windows go through cmd.exe, and a timed-out command's whole process tree is ended. A manual workflow, "App installers", builds the installers for all three systems.

- Remote control, steps 1 to 3 (Wi-Fi): the encrypted channel with one-time QR pairing, the computer-side host, **Settings > Remote** (on/off, keep awake, projects folder, extra allowed folders, QR pairing, paired phones, activity log), and the rules a phone's requests are checked against: only "ask first" or "plan only" (never auto-run), only inside the folders you allowed (checked on real paths, links followed), plain project names created inside the projects folder, rate limiting, and a log entry for each request. Running tasks, approvals, apply and undo moved into one controller shared by the desktop screen and a phone, with tests. The self-hosted relay package (`packages/relay`) is built but not used yet. See docs/REMOTE.md.

- App: **one model for Chat and Code by default**: choosing a model applies to both. The model menu (and Settings > Models) has "Same model for Chat and Code"; turning it off gives each mode its own model, which loads when you switch to it. Fixed: a suggestion chosen on the home screen reappeared in the message box after it was sent.

- App and engine: the **context window can be set up to 256K tokens** (Settings > Models: 4K to 256K). The engine reports the longest context the loaded model was trained for (`nCtxTrain`) and the attention-cache memory per token (`kvBytesPerToken`), and Settings shows what a full window can take for that model. A model is never asked for more than it was trained for (Llama 3.2 1B stops at 128K, Qwen3.5 reaches 256K). The cache is allocated lazily, so a short chat in a 128K window peaked at about 0.9 GB for the 1B model. The default stays at 4K; the agent now keeps more of its conversation when the window is larger. **Usage** also shows the agent's context.
- App: dialog headers have an icon tile, a title and a line saying what the dialog is for; buttons have a refined look (soft gradient primary, quiet outlined secondary, a distinct danger style, press feedback).

- App: **first-launch welcome** asks what to call you; the name is used in the home greeting and the sidebar, and can be changed in Settings > Profile. **One window**: on macOS the title bar is part of the app (traffic lights sit in the top row beside the sidebar toggle, back and forward, and the Chat/Code icons), and the row can be dragged to move the window. Back and forward move between the chats and sessions you opened.

Text and code files up to 1 MB, five at a time; images, PDFs and other binary files are refused with the reason, because the model reads text. Attachments are cut to fit the model's context (and the cut is shown), appear as chips on your message, and go to the model in fenced blocks after your words.

New settings: text size, suggestions on/off, notifications for background jobs and agent tasks, a Normal/Verbose transcript view for the agent, deleting all conversations or all coding sessions (with a second confirmation), and restoring default settings. Usage now lives inside Settings. Other dialogs share the same header bar.

- App: the layout follows a desktop coding app. Sidebar: mode icons (Chat, Code) at the top, New / Search / Background jobs, folding project and date headings with plain session names (a dot only for running, waiting for review or failed), and an account-style footer with Usage and Settings icons. Each task is shown as a transcript of steps (Read, Edited, Ran, Searched…), each a collapsible line that opens to its output or diff, ending in the agent's summary and a "files changed" card. A **side panel** shows the changes for review (Apply, Discard, Undo) and a browsable, filterable view of the project's files. Sessions are grouped by project in the sidebar with status dots (running, waiting for review, done, failed), are saved across restarts, and changes waiting for review survive a restart (unless over about 600 KB). The message box is now a compact bar: a **+** menu (Think, Browse, run in background, open another folder, tools, panel), permission mode, model picker and send.

- App: **browsing**. Chat has a Browse switch: the question is searched (DuckDuckGo's plain-HTML page, no key), the top pages are read as text, bounded to about 1,800 characters each, and given to the model with their sources, which appear as numbered chips under the reply. - App: the model is no longer loaded at launch (pinning several GB at once stalled the computer), and a model larger than 40% of RAM is not pinned.

### Added
- **Speed on the CPU engine** (Qwen3.5-9B, 16 GiB M2 Air, measured once with browsers open): decode 0.13 -> 8.3 tok/s, prompt processing 8.2 -> 19 tok/s. `--lock` pins the memory-mapped weights (`mlock`), so the operating system compresses other programs instead of evicting the model (the terminal chat turns it on by default for a model smaller than 60% of RAM; `--no-lock` turns it off; it is the 40-fold step). The Qwen3.5 forward pass reads prompts in batches of up to 32 tokens (`cl_fwd_prefill`; a weight block is unpacked once and multiplied with every token), the 5- and 6-bit weight kernels unpack with vector operations, and K-quant scales are unpacked with word operations. Results are unchanged (integer arithmetic is exact in any order): golden test, unit checks, chat protocol, sanitizers and 24-token greedy text against llama.cpp all as before. Details and the full table: docs/TEST_REPORT.md section 4b.
- **A sixth architecture, hybrid `qwen35` (Qwen3.5-9B)**: Gated DeltaNet linear-attention layers (a causal convolution, a per-head delta rule on a 128 x 128 state kept between tokens and between chat turns, a gated norm) alternating three to one with gated full-attention layers (output gate in the query projection, per-head QK-norm, rotary embeddings on a quarter of each head), a dense SwiGLU feed-forward in every layer, the `qwen35` pre-tokenizer, and a `Q5_K` integer dot-product kernel (NEON, AVX2, portable; the file uses Q5_K for the DeltaNet projections). Checked against llama.cpp on the real 5.2 GiB file: tokenization identical on 24 strings, token ids and top token identical on 6 prompts, greedy continuations identical for 24 tokens on 3 of 3 prompts, mean logprob gap 0.085-0.146 (docs/TEST_REPORT.md section 3e); the first layer agrees with llama.cpp's own tensors to about 1e-6. The golden test, `make chat-test` and the release workflow cover it (tiny generated model with an independent reference). The terminal chat uses the Qwen3.5 template (including its `<think>` block handling) and runs on Clutor's engine for this model. Memory-bound and without batched prompt processing: about 2 tok/s warm on a 16 GiB M2, and far slower when memory is short.
- **The terminal chat now runs on Clutor's own engine** for the architectures it supports (olmoe, qwen3moe, granitemoe, qwen2, llama). New `clutor-engine chat <model.gguf>`: a long-lived session over stdin/stdout (one JSON object per line) that loads the model once, keeps the KV cache between turns so a turn pays only for its new tokens, streams the reply token by token (UTF-8 characters split across tokens are held back until whole), samples with temperature, top-k, top-p and an optional repetition penalty and seed, and stops promptly on a `cancel` line. At temperature 0 it produces exactly the tokens `generate` does (checked on all five architectures by `c/test/chat_protocol.py`, `make chat-test`, also run in CI and before each release). The UI renders each model's chat template (ChatML, Llama 3, Granite, OLMo; Qwen3's `<think>` blocks are split out), sends only the text the engine has not seen, starts over when a conversation no longer extends the cache, and shows `/engine` (which engine, why, and what the last turn sent). A mixture-of-experts model larger than half the machine's memory is streamed from disk through an expert cache automatically, and each reply reports its cache hit rate and GB read. The coding agent uses the same engine. Models the engine cannot run yet (for example `qwen35`) fall back to `llama-server` and the UI says so and why; `--backend native|llama` forces one. The agent on the native engine has no grammar-constrained decoding (llama-server's), so it relies on the loop's reply validation. Measured on this machine (M2 Air, 16 GiB) with Llama 3.2 1B Q4_K_M in the terminal UI: about 28–31 tok/s, and the second turn of a conversation sent 15 new tokens to the engine rather than the whole history. The same 1B model is too small to drive the coding agent (it invented files and ran to the 30-step limit); that is the model's quality, not the engine's.
- **A new interactive chat in the terminal** (`clutor` with no command, or `clutor chat`, on a real terminal), laid out as a modern coding-assistant session. A two-column welcome panel (version in the border, tips, recent conversations); a rounded prompt box with history, multi-line input (`\` then enter, or paste), a filtering `/` command menu, `@file` attachments and `?` for shortcuts; replies stream word by word as rendered Markdown (headings, lists, aligned tables, code blocks with a gutter and syntax colours for JS/TS, Python, shell, C-family, Rust, Go, Java, SQL, JSON); an animated status line shows the phase (reading the prompt with its progress, thinking, writing), elapsed time and tokens so far; Esc stops a reply; a summary line gives measured tokens, tok/s and prompt size; the footer shows context use. **Shift+Tab cycles chat → agent → auto-apply.** In agent mode, messages are coding tasks and every tool call is shown as it happens (`● Read(file)`, `● Update(file)` with the removed and added lines, `● Run(command)` with a result line under each); the proposed changes are shown as a numbered, coloured diff and you answer with the arrow keys before anything is written (commands that run project code ask first, with a "don't ask again this session" choice); `/undo` restores the last applied task, `/verify <command>` makes a passing check a condition for offering changes. Commands: `/model` (any `.gguf` under `./models`, `./Models` or `~/.clutor/models`), `/think`, `/system`, `/temp`, `/compact`, `/clear`, `/resume`, `/copy`, `/save`, `/cost`, `/agent`, `/theme dark|light|ocean|mono` (remembered), and the existing `/status`, `/doctor`, `/plan`, `/bench`, `/pull`, `/init`. Models are found from any directory: under `./models` and `./Models` where you are, in `~/.clutor/models`, in the `models` and `Models` folders of the clutor checkout the command runs from, and in folders a model was chosen from before; the last model chosen is reused (`/model` changes it), and `clutor models` lists the same files. The model runs through `llama-server`, so any architecture llama.cpp supports works (not only the five the native engine runs), with no configuration file; closing the terminal in any phase also stops the server. The plain `clt>` session is still used when input or output is not a terminal, or with `CLUTOR_PLAIN=1`. Covered by 57 tests, including full sessions against a fake model server (chat; agent approve; agent discard) and a run against a real Qwen3.5-9B model, where the agent read a file, edited it and showed the diff.
- **A fifth architecture, dense `llama`** (Llama 3.2 1B Instruct): adjacent-pair rotary embeddings with Llama 3's `rope_freqs` factors, a BOS token added by default when the file has no `add_bos_token` key (llama.cpp's default for Llama 3 vocabularies), the `llama-bpe` pre-tokenizer (digits in groups of three, and a pre-token that is one vocabulary entry is used whole). Tokenization identical to llama.cpp on 24 strings, all 6 logit comparisons inside tolerance, greedy continuations identical for 24 tokens on 1 of 3 prompts (the others are near-ties; analysis in docs/TEST_REPORT.md). The golden test now covers five architectures (90 checks), and its Llama variant omits `add_bos_token` as the real file does. Listed in `clutor pull` and the planner catalog.

## 0.3.1

### Fixed
- **The release workflow no longer builds macOS arm64 on the retired `macos-14` image** (GitHub brownouts it now and retires it on 2026-11-02, which would have left a release without engine binaries); it uses `macos-15`.
- **`generate` now stops at any end-of-generation token**, not only the model's configured EOS: Qwen2.5 configures `<|im_end|>` but a base-style continuation ends with `<|endoftext|>`, and the engine used to run on past it and invent a "Human:" turn. It now stops on the same standard control tokens llama.cpp does (`<|endoftext|>`, `<|im_end|>`, `<|eot_id|>`, `<|end_of_text|>`, `<|end|>`, `<|eom_id|>`, `<end_of_turn>`, `</s>`).

### Measured
- OLMoE's greedy continuations were compared with llama.cpp for the first time: identical on 2 of 3 prompts; the third diverges at a near-tie where llama.cpp disagrees with its own batch evaluation (docs/TEST_REPORT.md).

## 0.3.0

### Added
- **Fixed: `/v1/decide` could return an unsigned answer.** The project roots are filled in asynchronously when the server starts, and `/v1/decide` did not wait for them, so a request that arrived early got `receipt: null` and no entry in the receipt log. It now waits like every other endpoint (found by a CI failure on a slow macOS runner; a regression test slows the startup step to reproduce it every time).
- **A fourth architecture, dense `qwen2`** (Qwen2.5-1.5B-Instruct): a plain SwiGLU feed-forward instead of experts, bias vectors on Q/K/V, tied output matrix; `--cache-mb` and `--smart` are refused on a dense model. Tokenization identical to llama.cpp on 24 strings, all 6 logit comparisons inside tolerance, but greedy continuations identical for 24 tokens on only 1 of 3 prompts (the other two diverge at near-ties; analysis in docs/TEST_REPORT.md). The planner now models tied embeddings, and `clutor pull` lists the model.
- **A stronger golden test**: the 8-bit integer kernels are now checked against a reference that applies the same activation rounding, agreeing to 5e-5 on all four architectures and all three kernel builds (72 checks), where before they were checked against a loose tolerance.
- **A third architecture, `granitemoe`** (IBM Granite 3.0 3B-A800M): no QK-norm, rotary embeddings on adjacent pairs, Granite's four scaling multipliers, tied-embedding fallback, and the `refact` pre-tokenizer (identical to llama.cpp on 24 strings). Checked on the real 1.9 GiB model: identical token ids and top token on 6 prompts, 98.4-99.0% router agreement, identical 24-token greedy continuations on 3 prompts; token logprobs differ more than on OLMoE (judged numerical noise). The architecture handling in `forward.c` is now a table. Listed in `clutor pull` and the planner catalog.

## 0.2.0

### Added
- **A real forward pass for `olmoe` models in the native engine**: byte-level BPE tokenizer, quantized weight readers (Q4_0, Q5_0, Q8_0, Q4_K, Q5_K, Q6_K, F16, BF16, F32), attention, router and experts. New engine commands `tokenize`, `logits`, `generate`. Checked against llama.cpp on OLMoE-1B-7B Q4_K_M: identical token ids on 10 test strings, same top-1 token on 6 prompts, 96.5-98% of visible router choices inside this engine's top-8 (see docs/NATIVE_ENGINE.md for the numbers and limits). Maps the whole file unless `--cache-mb` is given.
- **Experts streamed inside the real forward pass**: `generate --cache-mb N` reads each layer's experts from disk through the cache so resident memory is bounded by the cache. On OLMoE-1B-7B Q4_K_M: output byte-identical to the mapped run, peak RSS 544 MiB to 1.4 GiB against 3.7 GiB, but 2.3x to 5x slower than mapped because the run is disk-bound (about 1.4 GB/s on this SSD). Previous-token prefetch is optional and off by default: it raised hit rates but lost on time in every measurement. One run per setting, about 30% run-to-run spread; see docs/NATIVE_ENGINE.md.
- **SMART-ROUTE inside the real forward pass** (`--smart J,M,TAU` with `--cache-mb`) and a `quality` command (perplexity, KL divergence and top-1 agreement against exact routing). On OLMoE-1B-7B over 799 tokens of project text: mild settings read 12-14% fewer bytes per token for 2-3% higher perplexity and a different top-1 token at 6-10% of positions; unbounded cache-aware routing reads 25% fewer bytes but raises perplexity 2.7x.
- **Verification that needs no model**: `make -C c golden` / `golden-paths` generate a tiny runnable OLMoE (random Q4_K / Q6_K weights) and check the engine against an independent pure-Python forward pass; in exact float mode the two agree to 1e-4 on every kernel path, and the 8-bit integer path stays within a stated tolerance. `make -C c fuzz` corrupts model files thousands of ways under AddressSanitizer + UBSan. Both run in CI.
- **Qwen3-MoE** (Qwen3-30B-A3B family) in the forward pass: grouped-query attention, per-head QK-norm, renormalised expert weights, Qwen's pre-tokenizer (identical to llama.cpp on 24 strings). Checked against an independent reference on a tiny generated model and against llama.cpp on the real 17.3 GiB model: identical tokenization on 24 strings, 96.7-98.0% router agreement on three prompts, and identical 24-token greedy continuations on three prompts (token logprobs differ more than on OLMoE, which looks like numerical noise amplified by 48 layers; see docs/TEST_REPORT.md). Runs a model larger than RAM at 2-3 tokens/s with a 3-8 GiB footprint; the speed comparison against llama.cpp memory-mapping was not completed. The engine now refuses to map a file larger than 80% of RAM and asks for `--cache-mb`.
- `--prefetch ahead` (router-ahead predictor: 82% of its picks are chosen against 37% for `prev`) — accurate, but it does not cut time on a bandwidth-bound run, so prefetch stays off by default.
- **Fixed by that testing**: a corrupted tensor shape in a model file could make the forward pass write past a buffer (every tensor's shape and the hyper-parameters are now validated when the model opens); `logits` JSON could contain invalid UTF-8 for tokens that are half a character.
- **`clutor generate` and `clutor quality`** expose the real forward pass and the quality comparison from the main CLI, with live output; AVX2 integer kernels for Q4_K / Q6_K (compiled for x86_64, not yet executed by the author; CI will run them); `CLUTOR_FLOAT_MATH=1` runs the exact float path for diagnosis.
- **Prebuilt engine binaries**: `.github/workflows/release-binaries.yml` builds the engine on macOS arm64 / x86_64 and Linux x86_64 / arm64 on a version tag, runs the golden test on each binary, and attaches tarballs plus SHA256SUMS to the release; `clutor engine install` downloads the one for this machine, refuses it unless the SHA-256 matches, and installs it to `~/.clutor/bin` (tested against a local server; no real release exists yet).
- **`clutor pull`**: downloads now resume after an interruption (Range request, the `.part` file is kept) and are verified against the SHA-256 Hugging Face publishes for the file, deleting it on a mismatch; the OLMoE entry points at the exact file the engine was validated on, and Qwen3-30B-A3B (17.3 GiB, larger than 16 GiB of RAM) is listed.
- **Release workflow** skips a package whose version is already on npm instead of failing the run.
- docs/SCORECARD.md, docs/ROADMAP.md, docs/MODELS.md.
- **Faster compute**: integer dot products for Q4_K/Q6_K weights against 8-bit activations (NEON dot-product instruction), a persistent spinning thread pool and batched expert products take the forward pass from 0.30 to 0.03 s per token with the file in RAM, and bring the router closer to llama.cpp (99.8% of visible choices against an f32 KV cache).
- `generate --trace FILE` records the model's real router scores; `clutor stream --trace FILE` replays them through the cache, prefetch and smart-route code, and the report says `routing: real`. On one 130-token trace the old synthetic default overstated the hit rate (77% against 47%).

## 0.1.0

First release. Terminal only: there is no desktop app.

### Added
- **Interactive session**: `clutor` with no command in a terminal opens an interactive prompt. Plain text is a task for the sandboxed agent (diff, approval, receipt as before); `/` commands cover `/help /status /doctor /model /models /plan /simulate /inspect /bench /stream /pull /init /backend /ledger /decide /verify /yes /undo /tools /cost /history /clear /layers /cache /exit`. The model server starts once and stays up between tasks; earlier tasks are summarised to the next one; history is kept in `~/.clutor/history`; Ctrl-D leaves. `/cost` shows tokens reported by the model server, nothing estimated.
- **Native engine (`c/`)**: C11, no dependencies. GGUF v2/v3 reader; two-slot dense ring; expert streamer (`pread`, I/O thread pool, demand-before-prefetch); LRU, W-TinyLFU (4-bit count-min sketch, SLRU) and adaptive-window cache; prefetch staging pool; SMART-ROUTE (J, M, tau). Measures I/O, waits, hit rates and prefetch behaviour on a synthetic router. Does not run a transformer yet.
- **`@clutor/core`**: GGUF reader, memory planner and catalog (now including OLMoE-1B-7B and Qwen2.5-Coder-7B), cache simulator, drafting, the agent (strict tools, path jail, no-shell command policy, shadow workspace, diffs, apply/rollback), safety gates `CL-101..108`, ECDSA P-256 signed receipts.
- **`@clutor/cli`**: `clutor` and `clt` with `init`, `status`, `models`, `pull`, `inspect`, `plan`, `simulate`, `stream`, `bench`, `engine`, `chat`, `decide`, `code`, `serve`, `backend`, `receipts`, `ledger`, `receipt`, `rollback`, `doctor`; local OpenAI/Ollama/MCP server on :4320 (`POST /v1/decide` returns first-token choice probabilities and a signed receipt); llama-server supervision; JSON-schema-constrained tool calls and KV-prefix snapshots against llama-server.
- Tests: 158 core, 64 cli (including the C engine cross-checked against the TypeScript parser), 40,212 C unit checks, sanitizer runs, a smoke script.

### Changed
- `clutor code --verify` retries: a failing check is fed back (exit code and exact output, plus the task and how to read an assertion) for up to 3 self-healing turns; the final state must pass before `--apply` writes anything. The command typed after `--verify` runs without a prompt (it is the user's own command); one that only comes from the config file still asks. A verify command that was not approved is reported as "NOT RUN", not as a failure of the code.
- The agent's system prompt carries the project's module type and the `node:test` imports when no test framework is installed; its conversation limit follows the configured context size instead of a fixed 60,000 characters.
- `clutor plan --ram N` plans for an N GiB machine; the OS headroom is 22% of RAM clamped to 1.8-3.5 GiB. The plan labels the runtime line "Double-Buffer DMA (runtime buffers)".
- The engine's compute step is a Q4_0 x Q8_0 SIMD kernel (`--compute kernel|checksum`).
- `clutor bench` adds rows for scan-pollution rejects, prefetch hit/late, lookahead overlap and disk wait vs compute time.
- Receipts moved from HMAC to ECDSA P-256 with the public key inside the signed body, verifiable offline.
- The agent's first message is now the project map then the task, so tasks on a project share a cacheable prefix.

### Fixed
- **Engine memory**: expert buffers are packed in one arena at a 4 KiB stride instead of one page-rounded allocation each (16 KiB pages on Apple silicon made every slot about 5% too big), and the cache size is now budget / stride, so the cache never exceeds `--cache-mb`. Measured peak RSS = budget + staging + dense weights + about 3 MiB, flat across tokens.
- `clutor chat`, `decide`, `code` and `serve` failed to start llama-server on a machine without `~/.clutor/slots`; the folder is now created (mode 0700) first.

### Removed
