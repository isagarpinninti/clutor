# Changelog

Format follows [Keep a Changelog](https://keepachangelog.com/); versions follow [Semantic Versioning](https://semver.org/).

## Unreleased

- **Pictures, made inside Clutor.** Qwen-Image-2.1 (and other image models stable-diffusion.cpp runs) is linked into the app itself (stable-diffusion.cpp, MIT; a small C layer in `app/src-tauri/image/` calls it, and the build links it in when its libraries are found, so other builds simply report that the image engine is not included). Turn on "Image" in the chat box, describe the picture, pick 512, 768 or 1024: the chat model is unloaded (the two do not fit side by side in 16 GB), the picture is made with a progress bar and time left, and the chat model loads again on your next message. One call loads the model, makes the picture, saves a PNG and frees everything. The models folder picks the image model (a few-step Turbo model on a computer with little memory), and its text encoder and VAE. Measured on this Mac, 512 x 512 Turbo (8 steps, CFG 1): 155 s from a cold start in-process (the earlier command-line run was 197 s); peak memory 8.0 GB (7.1 GB with the options set this way in the earlier test, 15.9 GB without memory mapping). Not measured: 768 and 1024, other image models, and the full (non-Turbo) model through the app. Not yet: image-to-image editing, negative prompts, a choice of seed, batch pictures. Windows and Linux builds do not include the image engine yet.
- **Give Clutor a models folder; it works out the rest.** The app now reads the header of every GGUF and safetensors file in the folder (a few kilobytes each) and works out what it is: a chat model (and whether it is a mixture of experts), a picture-reading model with its projector, an image generator (a ComfyUI-style GGUF has no architecture name, so it is recognised by the names of its tensors) with its text encoder and VAE, or a file it cannot use (with the reason, for example an architecture the engine does not run). For each task it picks the most capable model that runs comfortably on this computer: chat, code (prefers a code-tuned model), a question about a picture (the picture-reading model, loaded automatically when you attach a picture), and image generation (a few-step model on a computer with little memory). A model measured at under one token a second loses to a faster one. The model menu has "Auto" (on by default; choosing a model yourself turns it off) and the model dialog shows what was found, what each task will use and why. Checked on the real folder on this Mac: five files understood correctly (found by testing: the Qwen-Image VAE names its tensors differently, which is now handled). The pick is a rule of thumb (size, mixture-of-experts, fit, measured speed), not a quality benchmark. Image generation itself is not wired in yet.
- **Qwen3-VL (qwen3vlmoe): text and pictures, and 2-bit / 3-bit weights.**
  - **Low-bit weights.** The engine now computes with Q2_K and Q3_K (it had Q4_0, Q5_0, Q8_0, Q4_K, Q5_K, Q6_K), with NEON integer dot products for one token and for batches. Checked: the dequantisers equal ggml's own on 2,000 random blocks each (linked against the installed llama.cpp), the integer dots equal dequantise-and-multiply, and a batched product equals the single-token product for every token.
  - **The language model.** `qwen3vlmoe` is Qwen3's mixture-of-experts model under another name; its multi-axis rotary embedding is the plain one for text. A tiny test model of that architecture matches the reference to 0.0003 (float) and 0.00005 (integer). On the real file (Huihui-Qwen3-VL-30B-A3B-Instruct-abliterated, imatrix Q2_K, 10.5 GiB, whose SHA-256 matches the publisher's): the tokens are identical to llama.cpp's on six prompts and the top-1 next token agrees on all six, but the log-probabilities differ by 0.1 to 0.65 on average. That is the model's sensitivity to rounding, not a bug: the engine's own integer and float paths differ from each other by 0.3 to 0.4 on the same prompts. Speed on this M2 with 16 GB, mapped, nothing else running: about 20 tokens/s generating once the file is in memory (0.05 s per token with 6 or 8 threads; the first run after the file was read from disk was 0.10 to 0.26 s) and about 15 tokens/s processing a text prompt (measured; the Q2_K kernels are young and not tuned).
  - **Pictures.** `c/src/vision.c` is the Qwen3-VL image encoder (27 transformer blocks with a two-dimensional rotary embedding, the DeepStack mergers after blocks 8, 16 and 24, the final 2 x 2 merger), reading the "mmproj" file. The language model takes the picture's vectors in place of text tokens with the model's own position scheme and adds the DeepStack features to its first three layers. The chat protocol takes `--mmproj FILE` and `{"op":"append","text":"...<|image_pad|>...","images":[{"w","h","rgb"}]}`; the app finds the projector next to the model and lets you attach pictures in chat (JPEG, PNG, GIF, WebP, resized to at most 256 tokens). Checked: the encoder equals an independent numpy implementation to 0.001% on all four outputs, and on a 448 x 448 test picture of three shapes the engine and `llama-mtmd-cli` give the same description (one phrase differs). Cost on this Mac: 7.7 s to encode a 448 x 448 picture and about 25 s to read its 196 tokens, so a picture question takes about 35 s before the answer starts. Not done: the coding agent does not take pictures, video input, and encoding more than one picture at a time on a big image is slow.
- **Cloud models from different providers.** Models > Cloud adds a provider (Anthropic, OpenAI, Google Gemini, OpenRouter, DeepSeek, Groq, Mistral, Together, Ollama or LM Studio on a computer you run, or any OpenAI-compatible address) with its API key, address, model names and context window, and its models appear in the model menu next to the local ones. Chat, background jobs and the coding agent work with them unchanged (the agent keeps its JSON tool protocol; replies may be 8,192 tokens when the window is 64K or more). The key is saved by the app's native side in a file only the app's user can read (mode 0600) and is added to the request there: the page never reads it back, and the request is made natively so providers' cross-origin rules do not block it. Using a provider needs a tick confirming that messages (and in coding mode the files the agent reads) are sent to it, and the cloud list says local models never send anything. Failures are explained (bad key, no credit, wrong model name, no connection) and a Test button checks a model. The model names in the presets are examples that may be out of date; every list is editable. Tested: request building and stream parsing for both API styles (unit tests) and the whole path in the preview with a canned answer. Not tested: a real request to any provider (no key was used), and the keys file is plain text rather than the system keychain.
- **Estimated times for the model you chose, and a safer pin.** The model check now says, for this computer: about how many tokens per second to expect, how long a chat answer and a small coding task (a page in three files) take, and how long the model takes to load, each as a range and labelled estimated or measured. The estimate adds the time to read the weights from memory and the time to read uncached experts from disk, with the cached share taken as (share of experts that fit) to the power 0.6; that fit comes from one measurement (Qwen3-30B-A3B on an M2 with 16 GB: it gives 3 to 6 tokens per second where 4.7 was measured), so it is a rough guide, and the memory speed (40 GB/s) is an assumption. Once a model has answered, its measured speed replaces the estimate, and the coding view says what a small task will take on it; while a task runs, the time left is estimated from how long the finished plan steps took. A model under half a token per second is called very slow. Engine: a model is only pinned in memory (the lock) when it is at most 60% of the machine's memory and 90% of what is free; a bigger one used to be pinned or read in whole before the engine decided to stream it, which could starve the whole machine. Not measured: the estimate for models other than the one above, on dense models bigger than memory (they run through the system's paging and are slow), and on other computers.
- **A lighter, smoother coding mode.** The transcript is flat (your message is a soft bubble on the right, replies and steps are plain text, the changes card is a quiet block instead of a bordered box), steps use small monospace lines, motion is short (110 to 180 ms) and limited to fades and small moves, and the conversation scrolls smoothly (not with reduced motion on). Earlier tasks are skipped by the browser's layout and paint work until they are on screen (`content-visibility`), and a step group is only redrawn when its own steps change, so a long session stays quick as steps arrive. Not measured: no frame-rate numbers were taken; the change is from the structure and the preview.
- **Hooks, helpers, saved permissions, bigger stage animation.** `.clutor/hooks.json` in a folder can run commands around the agent's steps: `PreToolUse` (a failure blocks the call), `PostToolUse` (the output is shown to the model) and `Stop` (a failure sends the agent back to work, up to three times). They use the same allowed programs as `run_command` and need no approval, but they run in the scratch copy, so they check the work (tests, a linter) and cannot change your folder; `/hooks` shows what was loaded. The agent has a `delegate` tool: it hands a question to a read-only helper (reads and searches only, at most 8 steps, no nested helpers) and gets its report, which keeps a big project out of its own context; on the local engine this makes the model read its conversation again, so it costs time on a slow machine. The command approval also has "Always allow this command here" (kept per folder across restarts, never for the network; `/permissions` lists them, `/revoke` removes them). The spinning animation next to the stage text, the steps and the plan is larger.
- **Rewind, `@file` mentions, `/init`.** A rewind button on each task (and `/rewind`) puts the folder back to how it was before that task (that task's changes and every later one are undone, newest first), removes it and the later tasks from the session and puts its text back in the prompt box; nothing is undone further if a file was edited by hand since. Typing `@` in the prompt box lists the project's files; the files named are read (6,000 characters each, five at most) and given to the agent, while the task shows only what you typed. `/init` asks the agent to read the project and write a `CLUTOR.md` for it. A closed app already brings its sessions back with their transcript, and a task cut off by closing is marked interrupted with a "Try again" button; it does not resume mid-task.
- **Coding mode, closer to Claude Code (first batch).** Slash commands in the prompt box (`/help /clear /compact /undo /plan /ask /auto /context /diff /model /tools`) with a menu, arrow keys and Tab; type while a task runs and the message is queued (shown above the box, removable) and runs next; Esc stops the task; the up arrow brings back earlier tasks; a "62% context" meter turns amber past 80%. Each task now knows what the earlier ones in the session did and which files they made (so "now add a score" works and files are not made again); `/compact` makes later tasks forget them. Project instructions are read at the start of every task from `CLUTOR.md`, else `AGENTS.md`, else `CLAUDE.md` in the folder. The command approval has "Allow once" and "Allow for this session" (never for commands that use the network). Not done yet: resuming a session with its full conversation after a restart, a rewind to an earlier checkpoint, `@file` mentions, sub-agents, hooks.
- **A coding transcript that keeps you company.** Steps that follow each other are one line, "Read 2 files, wrote 1 file, ran 3 commands", which opens to each step (and each step to its output or change); the step being worked on says what it is doing ("Running npm test…") and stays open. The live line has a word that changes every few seconds while the model is thinking (Pondering, Brewing, Tinkering…), the total time and the tokens written so far; a finished task ends with "Worked for 2m 14s · 6 steps · 1,830 tokens". The prompt box lights up when focused, and its note under it now says when files are written (it still said every change was shown first). The step count and tokens are measured; the live token count is an estimate (characters / 4).
- **A task's files are written to the folder when it ends.** Until now every change was held aside until you pressed "Apply to folder", so the folder stayed empty and the next task started from the old files and made them again. A task started on this computer now writes its files when it ends (also when it was stopped or failed part-way, so the work is not lost), keeps an undo point (Undo restores the folder), and writes nothing if the files in the folder changed meanwhile (the error says so). A plan-only task writes nothing, and a task started from another device still waits for review on this computer. Within one task, writing a file again with exactly the same content is refused with a note to move on.
- **Long files are no longer cut off and lost; the plan ticks; diffs show what changed; the side panel fits.** A reply that hit the length limit in the middle of a tool call (a long file) was discarded and the model was told to write smaller files, so a page never got written. Now the agent continues the same reply from where it stopped (up to three more times, in the same engine conversation, with no re-read of the prompt) and only falls back to the old message when that fails. A plan step that names a file is ticked when the file is written, and every step is ticked when the task finishes (a weak model rarely updates its own plan). Diffs show the added and removed lines with one line of context, the first 40 lines, and a button for the rest (a new file is all added lines); the live preview of a file being written shows its last 8 lines. The side panel scrolls (its sections shrank instead of overflowing), and no longer ends up outside the window in a narrow window (a style I added last round overrode its placement).
- **The coding agent no longer plans in circles, and the conversation compacts itself.** On a 4,096-token window the agent's instructions plus one page of HTML filled the window: replies were cut off at 1,024 tokens, discarded, and the model re-planned from the start each time (on a slow machine, about every 4 to 5 minutes). Fixes: the default context window is now 8,192 tokens (a saved 4,096 is raised to it); the instructions tell the model to keep each file to about 80 lines and to split a page into `index.html`, `style.css` and `script.js`; and when old steps no longer fit, they are replaced by a short record of what was done plus the current plan, instead of being silently dropped (the agent emits a `compact` event and the session shows a note). Chat compacts too: when the context is 80% full the next message is preceded by a model-written summary of the conversation so far. Measured: the new tests pass (agent compaction, chat compaction); not yet measured: how much faster a real 30B run finishes a page, since a cut-off reply is expensive only on a slow machine.
- **Coding mode panels.** The progress view is now at the top of the Session tab (there is no separate Progress tab), with an activity list under it that shows every step: files written or edited with +/- counts and their changes, and commands with their output. While a task runs, a one-line status stays at the top of every other tab. The sidebar and the side panel can be resized by dragging their edge (or with the arrow keys; double-click resets) and the widths are remembered. The window opens at 1440 by 900 (it was 1100 by 760).
- **Engine speed.** Prompt processing is now batched for every architecture (it was only batched for qwen35): each weight matrix is read once per batch of up to 64 prompt tokens, and in a mixture-of-experts layer each chosen expert is read once per batch for all the tokens that picked it (so a long prompt streamed from disk reads each expert once per layer-batch instead of once per token; verified for correctness on the test models, not yet measured on a large MoE). The 128,000-word output layer is computed for the last prompt token only. Attention runs across all threads (one task per head and token), which matters most at long contexts, and the half-precision conversion in the matrix kernels uses the processor's own instruction. The batched path gives **bit-identical logits** to stepping token by token on all six architectures, mapped and streamed, at several batch sizes (new `make prefill-test`, in CI, also under ASan and TSan). On the development Mac (M2, Llama 3.2 1B Q4_K_M, same-session measurements): prefill 38 to 84 tokens/s at ~500 tokens of context, 18 to 59 at ~2,000 and 9.5 to 26 at ~6,000; generation 26 to 29, 14 to 24 and 6.4 to 13 tokens/s. A first run measured up to 4x for prefill; this machine's speed varies with load, so the conservative same-session figures are the ones to trust. Generation speed on short contexts is limited by memory bandwidth and did not change much.
- **The key/value cache is half precision: half the memory, and faster attention.** It was stored as single-precision floats (196,608 bytes per token on Qwen3-30B-A3B, 6.4 GB for a 32K-token conversation); it is now half precision (98,304 bytes per token, so the same memory holds twice the context, and the engine reports the new figure so the app's context-window text follows). Attention converts on the way into the multiply-add. Measured on Qwen3-30B-A3B Q4_K_M at a 2,702-token context (one run each, on battery power, which makes timings noisy): attention 27 ms to 18 ms per generated token, prompt processing 23.3 to 27.7 tokens/s; with the previous attention change, attention is 89 ms to 18 ms and prompt processing 16.2 to 27.7 tokens/s. The cost is accuracy: a cached value is rounded to 11 bits, about 5e-4 relative. The tests compare against a reference that rounds the same way, and now allow the rare one-step differences when the engine (single precision) and the reference (double) round a value on opposite sides of a boundary: float path 0.015 maximum (seen up to 0.005, was 0.0002), integer path 0.4 maximum (seen up to 0.17); a wrong operation shows up as 0.1 to several in the float path. The converter is tested against a software reference on 4 million values.
- **Faster attention on long contexts (the coding agent's case).** One token's attention now reads each key and value once per group of query heads that share them, in chunks of positions spread over the threads, with the multiply-adds blocked four positions at a time on the vector unit (ARM NEON; other processors use the vectorisable scalar version); the attention scores everywhere use a vectorisable dot product. Measured on Qwen3-30B-A3B Q4_K_M on a 16 GiB, 8-core Mac at a 2,702-token context: attention 89 ms to 27 ms per generated token, decode 4.6 to 6.3 tokens/s, prompt processing 16 to 23 tokens/s (one run each; the disk-bound part of each run varies by about 10%). In isolation, at the model's real shape, one layer's attention at 5,600 positions takes 0.94 ms instead of 2.9 ms. The new path is checked against a double-precision reference on random data (`make test`, 4 head layouts, 3 softmax sharpnesses, 3 chunk lengths) and end to end through the prompt/step test. `CLUTOR_PLAIN_ATTENTION=1` selects the old one-head-per-task code.
- **The coding agent no longer fails silently or claims work it did not do.** A task that asked for a whole page failed with "the reply was not a tool call" and then reported success with no file written. Causes and fixes: replies were capped at 1,024 tokens, which cut a long file off in the middle of its tool call (the cap is now a quarter of the context, up to 4,096, in the app and the terminal); models put raw line breaks inside the JSON string, which is now read leniently; a reply that is cut off gets a specific instruction to write smaller files. The agent now sends a `finish` back to work if nothing was read, written or run yet (twice at most), and if the task or the summary names files that do not exist (twice at most). The tool prompt shows how to create a file, asks for complete working files, and adds an `update_plan` tool. If the model never uses a tool, its last answer is shown with an explanation instead of a made-up summary, and a task that ends with no file changed says so with a Try again button. Measured on Qwen3-30B-A3B Q4_K_M, the same task: before the fix, no file written; after, the page is written without error, and the model, sent back for the files it named, goes on to write the others (one run each; the quality of what a model writes is still the model's).
- **Coding mode shows where a task is.** The agent writes a plan that appears as a checklist and ticks off as it works; with no plan, the stages (Plan, Explore, Write, Check) and a line saying what it is doing now, instead of "Working...". Pressing Enter scrolls to the new task, so it is clear it started. Problems are one consistent alert (an icon, a title, a plain explanation, Try again); a routine recovery ("the model answered in text, so it was asked again") is a quiet hint that merges repeats.
- **The automatic expert cache no longer pushes other programs into swap.** It was 45% of the machine's total memory, whatever else was running. With another program holding a lot (a 30B model open in the app, say), that cache and the other program together exceeded memory, the system swapped (8.9 GB of swap was in use) and decoding slowed by a factor of 20 to 40 (3.9 s per generated token in one measurement; the same model normally runs at 0.15 s). It is now 45% of total memory but at most 60% of the memory that is free or reclaimable right now (free, inactive and speculative pages on macOS, `MemAvailable` on Linux, available physical memory on Windows), never below 256 MiB and never more than all the experts. On the machine above, with 3.2 GiB reclaimable, it chose 1.9 GiB instead of 7.2 GiB. Unit tests cover the rule; `CLUTOR_FAKE_AVAIL_BYTES` sets the figure for tests. Close the other programs that use a lot of memory (or the second copy of the model) before measuring speed.
- **Coding mode: progress in the panel, live.** The four stage pills are gone. The model's reply is now streamed to the screen while it is being written (a long reply used to show nothing until it was finished, and appeared all at once when you pressed Stop), and the right panel opens by itself when a task starts, on a new **Progress** tab: the task, the plan as it ticks off (read from the half-written reply, so it fills in as the model writes it), what the agent is doing right now with how long it has been at it, the file it is writing as it is written, and the steps so far. When the task ends with changes to review, the panel moves on to Changes. The conversation keeps one quiet line ("Writing index.html... 12s") with a link to the panel. Pressing Stop drops the half-written reply instead of acting on it. Motion is shorter and lighter: the panel slides and fades in about 0.2 s, content fades in about 0.15 s, and only opacity, transform and width are animated.
- **Coding mode: a timer and task actions.** While a task runs, the current stage (or plan step) shows how long the agent has been in it, restarting when it moves on, and the total time since the task started. Your task has Copy, Edit (then run the edited task) and Redo (run it again), as in chat.
- **Chat message actions.** Your messages have Copy, Edit (resends from there and replaces what followed) and Redo; replies have Copy and Regenerate.
- **Models bigger than your memory now load by themselves.** A mixture-of-experts model larger than 80% of the machine's memory used to be refused unless you passed `--cache-mb`, which the app never did, so the app could not open one. Now the engine streams its experts from disk automatically, with a cache of 45% of memory (capped at the size of all the experts) and the settings that measured best; a dense model that does not fit still refuses, and says why. The ready event reports `autoStream`, and the app shows "streaming from disk". Measured on Qwen3-30B-A3B Q4_K_M (17.3 GiB) on a 16 GiB, 8-core Mac, opened the way the app opens it (no flags): loads at once, 8.5 tokens/s over 200 generated tokens, 97.8% cache hits; one run. Cache size matters a great deal (300 tokens each, nothing else running): 4 GiB 4.7 tokens/s (disk-bound), 8 GiB 10.1 tokens/s, 11 GiB 4.3 tokens/s (slow again, in expert compute, which looks like memory pressure; the cause is not confirmed), hence 45%. The router's dot products, which took 22 ms of every 120 ms token, now use the vector unit (5 ms). `CLUTOR_PROFILE=1` also profiles generation. A new test (`npm run engine:autostream`) pretends the machine is small and checks that each architecture streams, says the same thing as the mapped run, and that dense models refuse clearly.
- App: **a fresh look.** Completely dark (near-black, neutral greys) with one flat, deep royal blue in two tones (`#4a68f5` for the mark, text and outlines, a deeper `#3150e0` for filled buttons) used with restraint: quiet outlines on the toggles that are on, a faint focus ring, no gradients anywhere. A **light theme** too: **Settings > Appearance > Theme** has Dark, Light and System, applied before the first paint. A new mark: a cluster of seven cells, the experts of a mixture-of-experts model, five lit in the shape of a "C" (the experts that are loaded and working) around a dim one (the rest of the model, which stays on disk), which is how Clutor runs a model much bigger than the machine. While the model thinks the cells light up one after another, which is the router choosing experts; while a reply streams they breathe together. New app icon on every platform. Home screen: the mark beside the greeting, a wide message box with **Think** and **Browse** as visible toggles (they were hidden in the + menu), and four quiet starter chips. Replies: a soft entrance, a pulsing dot at the end of streaming text, a stop button with a turning ring, and a reasoning card titled "Thinking" while it works and "Thought for N s" after (measured while the message is on screen; an older message just says "Thought process"). Spacing follows one rhythm (4, 8, 12, 16 px): the toggles under the message box no longer touch, its padding is even, its controls share one height, and the message box lines up with the thread. Rounded corners are for the buttons (compact controls are pills, send and stop are circles), the message box and the chat (your messages, code blocks, tables, the reasoning card); dialogs, settings and other cards have square corners. The sidebar header sits on one grid: the mark, the icons and the account avatar share a centre line, and the labels start at the same place. All motion respects the system's reduced-motion setting.
- **Faster prompts when the model streams from disk.** When experts are read from disk, prompt processing now takes up to 256 tokens per batch (64 when the model is in memory) and asks for the next group of experts while the current one computes. Measured on Qwen3-30B-A3B Q4_K_M (17.3 GiB) on a 16 GiB, 8-core Mac, 1,351 prompt tokens through `chat` with a 4 GiB expert cache: 5.9 tokens/s before, 9.7 after, same day, one run each. Disk read per 383-token piece fell from 57.6 GB to 28.0 GB. Decode speed is unchanged (about 3 tokens/s). Fixed on the way: a batched product silently clamped to 64 tokens, which would have dropped tokens in a larger batch (now 256, with a compile-time check). `chat` now reports cache hit rate, GB read and wait time for the prompt in its `appended` event. The tests gained long-prompt cases with 256- and 100-token batches (the tiny test models now allow 512 tokens of context).
- **Prompt processing, round two (streamed models).** The router's dot products now run across the thread pool (they were a serial loop, a fifth of the time; results identical), and a batch holds up to 512 tokens when experts stream (about 50 MB more scratch memory on this model; it was 256). A prompt of N tokens now costs about N/512 passes over the model's experts. `CLUTOR_PROFILE=1` prints where a prompt's time went (norms, projections, attention, routing, waiting for experts, expert products). Measured on Qwen3-30B-A3B Q4_K_M, 16 GiB / 8-core Mac, 4 GiB expert cache, the same 1,351 prompt tokens through `chat`, one run each: 5.9 tokens/s at the start of this work, 9.7 after the first round, 23.0 now (58.8 s). Disk read for the first 383 tokens: 57.6 GB, then 28.0, now 15.5. Speed drifted by about 15% between sessions on this machine, so compare only runs from the same hour. A deeper read-ahead made no difference (1 to 8 groups ahead, same speed): with a 4 GiB cache the prompt is close to the disk's measured top speed. Later pieces run slower (29 tokens/s for the first, 17 for the fourth) as the context grows.
- Fixed a data race (found by ThreadSanitizer) in the lazily initialised float-math flag that every pool thread reads.

- **Will it run?** In the app, each model has a "Will it run?" check: it reads only the model's header and says whether the model fits, where the memory goes, and the fastest the disk could let it generate (computed upper bounds), with **Measure this disk** to replace the assumed 3 GB/s by a timing of the model's own file. The terminal app has the same: `clutor plan <file.gguf> --measure-disk` (via the new engine command `clutor-engine diskbench`). On the development Mac the measured scattered read speed was 1.27 GB/s, not the assumed 3.
- **Windows and Linux:** the desktop app is now built and tested by CI on macOS, Windows and Linux (it had only ever been compiled on macOS). The engine gained a small threading layer so it builds with the normal Windows compiler (clang-cl); commands the agent runs on Windows go through cmd.exe, and a timed-out command's whole process tree is ended. A manual workflow, "App installers", builds the installers for all three systems.

The model menu (and Settings > Models) has "Same model for Chat and Code"; turning it off gives each mode its own model, which loads when you switch to it. - App and engine: the **context window can be set up to 256K tokens** (Settings > Models: 4K to 256K). ### Added
- **Speed on the CPU engine** (Qwen3.5-9B, 16 GiB M2 Air, measured once with browsers open): decode 0.13 -> 8.3 tok/s, prompt processing 8.2 -> 19 tok/s. `--lock` pins the memory-mapped weights (`mlock`), so the operating system compresses other programs instead of evicting the model (the terminal chat turns it on by default for a model smaller than 60% of RAM; `--no-lock` turns it off; it is the 40-fold step). The Qwen3.5 forward pass reads prompts in batches of up to 32 tokens (`cl_fwd_prefill`; a weight block is unpacked once and multiplied with every token), the 5- and 6-bit weight kernels unpack with vector operations, and K-quant scales are unpacked with word operations. Results are unchanged (integer arithmetic is exact in any order): golden test, unit checks, chat protocol, sanitizers and 24-token greedy text against llama.cpp all as before. Details and the full table: docs/TEST_REPORT.md section 4b.
- **A sixth architecture, hybrid `qwen35` (Qwen3.5-9B)**: Gated DeltaNet linear-attention layers (a causal convolution, a per-head delta rule on a 128 x 128 state kept between tokens and between chat turns, a gated norm) alternating three to one with gated full-attention layers (output gate in the query projection, per-head QK-norm, rotary embeddings on a quarter of each head), a dense SwiGLU feed-forward in every layer, the `qwen35` pre-tokenizer, and a `Q5_K` integer dot-product kernel (NEON, AVX2, portable; the file uses Q5_K for the DeltaNet projections). Checked against llama.cpp on the real 5.2 GiB file: tokenization identical on 24 strings, token ids and top token identical on 6 prompts, greedy continuations identical for 24 tokens on 3 of 3 prompts, mean logprob gap 0.085-0.146 (docs/TEST_REPORT.md section 3e); the first layer agrees with llama.cpp's own tensors to about 1e-6. The golden test, `make chat-test` and the release workflow cover it (tiny generated model with an independent reference). The terminal chat uses the Qwen3.5 template (including its `<think>` block handling) and runs on Clutor's engine for this model. Memory-bound and without batched prompt processing: about 2 tok/s warm on a 16 GiB M2, and far slower when memory is short.
- **The terminal chat now runs on Clutor's own engine** for the architectures it supports (olmoe, qwen3moe, granitemoe, qwen2, llama). New `clutor-engine chat <model.gguf>`: a long-lived session over stdin/stdout (one JSON object per line) that loads the model once, keeps the KV cache between turns so a turn pays only for its new tokens, streams the reply token by token (UTF-8 characters split across tokens are held back until whole), samples with temperature, top-k, top-p and an optional repetition penalty and seed, and stops promptly on a `cancel` line. At temperature 0 it produces exactly the tokens `generate` does (checked on all five architectures by `c/test/chat_protocol.py`, `make chat-test`, also run in CI and before each release). The UI renders each model's chat template (ChatML, Llama 3, Granite, OLMo; Qwen3's `<think>` blocks are split out), sends only the text the engine has not seen, starts over when a conversation no longer extends the cache, and shows `/engine` (which engine, why, and what the last turn sent). A mixture-of-experts model larger than half the machine's memory is streamed from disk through an expert cache automatically, and each reply reports its cache hit rate and GB read. The coding agent uses the same engine. Models the engine cannot run yet (for example `qwen35`) fall back to `llama-server` and the UI says so and why; `--backend native|llama` forces one. The agent on the native engine has no grammar-constrained decoding (llama-server's), so it relies on the loop's reply validation. Measured on this machine (M2 Air, 16 GiB) with Llama 3.2 1B Q4_K_M in the terminal UI: about 28–31 tok/s, and the second turn of a conversation sent 15 new tokens to the engine rather than the whole history. The same 1B model is too small to drive the coding agent (it invented files and ran to the 30-step limit); that is the model's quality, not the engine's.
- **A new interactive chat in the terminal** (`clutor` with no command, or `clutor chat`, on a real terminal), laid out as a modern coding-assistant session. A two-column welcome panel (version in the border, tips, recent conversations); a rounded prompt box with history, multi-line input (`\` then enter, or paste), a filtering `/` command menu, `@file` attachments and `?` for shortcuts; replies stream word by word as rendered Markdown (headings, lists, aligned tables, code blocks with a gutter and syntax colours for JS/TS, Python, shell, C-family, Rust, Go, Java, SQL, JSON); an animated status line shows the phase (reading the prompt with its progress, thinking, writing), elapsed time and tokens so far; Esc stops a reply; a summary line gives measured tokens, tok/s and prompt size; the footer shows context use. **Shift+Tab cycles chat → agent → auto-apply.** In agent mode, messages are coding tasks and every tool call is shown as it happens (`● Read(file)`, `● Update(file)` with the removed and added lines, `● Run(command)` with a result line under each); the proposed changes are shown as a numbered, coloured diff and you answer with the arrow keys before anything is written (commands that run project code ask first, with a "don't ask again this session" choice); `/undo` restores the last applied task, `/verify <command>` makes a passing check a condition for offering changes. Commands: `/model` (any `.gguf` under `./models`, `./Models` or `~/.clutor/models`), `/think`, `/system`, `/temp`, `/compact`, `/clear`, `/resume`, `/copy`, `/save`, `/cost`, `/agent`, `/theme dark|light|ocean|mono` (remembered), and the existing `/status`, `/doctor`, `/plan`, `/bench`, `/pull`, `/init`. Models are found from any directory: under `./models` and `./Models` where you are, in `~/.clutor/models`, in the `models` and `Models` folders of the clutor checkout the command runs from, and in folders a model was chosen from before; the last model chosen is reused (`/model` changes it), and `clutor models` lists the same files. The model runs through `llama-server`, so any architecture llama.cpp supports works (not only the five the native engine runs), with no configuration file; closing the terminal in any phase also stops the server. The plain `clt>` session is still used when input or output is not a terminal, or with `CLUTOR_PLAIN=1`. Covered by 57 tests, including full sessions against a fake model server (chat; agent approve; agent discard) and a run against a real Qwen3.5-9B model, where the agent read a file, edited it and showed the diff.
- **A fifth architecture, dense `llama`** (Llama 3.2 1B Instruct): adjacent-pair rotary embeddings with Llama 3's `rope_freqs` factors, a BOS token added by default when the file has no `add_bos_token` key (llama.cpp's default for Llama 3 vocabularies), the `llama-bpe` pre-tokenizer (digits in groups of three, and a pre-token that is one vocabulary entry is used whole).
