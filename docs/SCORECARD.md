# Scorecard

How Clutor rates against its own bar and against Colibri and AirLLM (docs/BENCHMARKS.md), kept in the repo so the ratings can be argued with. A score is only raised when the evidence column can be re-run or inspected; anything that needs other people (users, contributors) or a measurement not yet taken is marked as such and is not scored.

Last updated after the 0.2.0 release (npm and a GitHub release with engine binaries for four platforms). Scale: 10 is "nothing material left to ask for". 9.5 is the project's target on every row; it is not reached yet, and the last column says what it would take.

| Criterion | Now | Evidence (re-runnable) | What 9.5 needs |
|---|---|---|---|
| Model coverage | 6 | Six architectures run end to end, each checked against llama.cpp: `olmoe` (OLMoE-1B-7B), `qwen3moe` (Qwen3-30B-A3B), `granitemoe` (Granite 3.0 3B-A800M), the dense `qwen2` (Qwen2.5-1.5B) and `llama` (Llama 3.2 1B), and the hybrid `qwen35` (Qwen3.5-9B, Gated DeltaNet). `docs/MODELS.md` | Six architectures with a real forward pass, each checked against llama.cpp: a seventh is needed (DeepSeek-style with latent attention, or Mixtral-style with a SentencePiece tokenizer); `qwen35` is the first non-attention-only design, but the engine has no batched prompt processing, so a long prompt on a 9B model is slow; the two dense models' greedy match with llama.cpp is weaker than the MoE models' (1 of 3 prompts identical for 24 tokens each) |
| Speed on the models it runs | 8 | OLMoE: 9.6-9.9 s for the 100-token job against 15.4-16.9 s for Colibri (docs/BENCHMARKS.md). Qwen3: 2.0-3.0 tokens/s out of core, not compared with anything yet | The same comparison on 3+ models and a second machine, including Qwen3 against llama.cpp memory-mapping |
| Memory efficiency | 9 | OLMoE runs from 481 MiB to 1.4 GiB RSS on a 3.9 GiB model; Qwen3 runs a 17.3 GiB model in 2.9 GiB (2 GiB cache) to 8.1 GiB (8 GiB cache) | Held across more models |
| Larger-than-RAM models | 6 | Qwen3-30B-A3B Q4_K_M (17.3 GiB) on a 16 GiB machine: 2.04-3.03 tokens/s at 2, 4 and 8 GiB caches, 3 runs each (docs/TEST_REPORT.md). Parity with llama.cpp on that file: identical tokenization on 24 strings, 96.7-98.0% router agreement, identical 24-token greedy continuations on 3 prompts. The roadmap's pre-registered checks (peak RSS under 8 GiB at the smaller caches, top token on at least 5 of 6 prompts, at least 95% routing agreement) all passed | The speed comparison against llama.cpp memory-mapping on the same cold file, 3 runs each (the llama.cpp half was started and stopped, so no ratio is claimed); explain the larger logprob gaps than on OLMoE (judged numerical noise, not proven); a second large model |
| Correctness checking | 9 | `make -C c golden-paths` (independent pure-Python forward pass for all six architectures; float math agrees to 8e-5 and the 8-bit integer path to 5e-5 on every kernel path, including the AVX2 build on a real x86 Linux runner), `verify-llama` / `verify_greedy.py` / `verify_tokenizer.py` / `compare_routing.py` against llama.cpp, 4,200 fuzz runs clean, 270 TypeScript and 41,811 C checks (docs/TEST_REPORT.md) | Held on every added architecture; a perplexity comparison with llama.cpp on a long text |
| Honest reporting | 9 | Every figure is labelled measured / computed / assumed / simulated; wrong numbers were corrected in the docs with the reason (the cache-warmed streaming result, the mis-aligned routing check); the Qwen3 benchmark is reported as partial | Keep it: a third party reproducing a table from `scripts/bench/` |
| Install and ease of use | 6 | `npm i -g @clutor/cli@0.2.0` then `clutor engine install` was run end to end against the real release on macOS arm64 (isolated home): downloaded, SHA-256 verified, installed, and the CI-built engine generated text. `clutor pull` resumes interrupted downloads and verifies the publisher's SHA-256 (unit-tested against a mock server; not yet used for a live model download) | The installer run on Intel macOS and on Linux; `clutor pull` used for a live download; a single documented command from nothing to generated text |
| Maturity | 6 | 0.2.0 is published on npm (`@clutor/core`, `@clutor/cli`) and as a GitHub release with engine binaries for macOS arm64 / Intel and Linux x64 / arm64 plus SHA256SUMS; CI green on the release commit on Linux and macOS (unit tests, golden test, sanitizers, fuzzing, dependency audit); a release workflow that skips already-published versions; SECURITY / CONTRIBUTING / issue templates | A stated compatibility and deprecation policy; Windows or a stated decision not to support it; a second maintainer able to release; a month of releases without a corrective one |
| Community | not scored | Needs people other than the author: outside users, issues, contributors, independent reproductions of the benchmarks | Outside contributors merged, benchmark results submitted from other hardware, issues answered within a stated time. `docs/ROADMAP.md` lists what is built to invite them; none of it counts until others act |

Unweighted mean of the rows that are scored: **7.4/10** (6, 8, 9, 6, 9, 9, 6, 6 = 7.375; was 7.25, 7.0 after the 0.2.0 release, and about 6.4 before it). One row is deliberately not scored. Reaching 9.5 means every scored row at 9.5 and the community row measured, which today is not true and cannot be made true by the author alone. The biggest single gaps are model coverage (6) and the missing speed comparison on the one large model.
